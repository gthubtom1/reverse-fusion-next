# 聚合精简方案：REA核心＋按需Reverse＋薄适配层

日期：2026-11-18。状态：S0→S4工程实施与收尾完成；未发布，产品/模型净收益未建立。最终结果见[SLIM-RESULT.md](SLIM-RESULT.md)。

实施只修改本工作区的自有实现、指引和测试；官方包、用户配置及已有成果保持。未授权提交、推送或部署切换。
基线是fix/independent-audit-nine工作区中已经完成9项修复的实际文件，不是仅凭HEAD：这些修复尚未提交。

## 1. 决定与边界

目标不是减少文件数或工具数，而是让当前智能体用更少的重复规则和记账，可靠推进用户的完整目标。
选择小步兼容改造，不重写整套系统：保留官方REA和现有有效工程设施，让自有层退出重复的专业验收职责。
保留当前宿主作为唯一推理和编码者；不恢复强制Craft/Spec，不增加第二模型或常驻推理循环。

合格的最终形态：

- 用户只说目标和补充，不选组件、工具或专业路线。
- 普通开发保持宿主原生；简单分析不承担完整复刻账本。
- Reverse提供按需专业经验，不另起阶段控制或账本。
- REA及实际专业工具产出原生分析、观察、比较、未知项和适用判据。
- 薄层保存用户要求、连接这些结果、处理平台缺口和磁盘/部署/恢复；状态从结果派生。
- 实际证据不够时保留缺口，继续无依赖工作，不用增加文档把缺口变成完成。

## 3. 一份项目视图，不再手工维护两套技术状态

职责明确分开，而不是把所有东西塞进一个JSON：

| 信息 | 权威来源 | 项目视图保存什么 |
|---|---|---|
| 用户要什么、补充了什么 | 用户原话与项目需求 | 原文、稳定需求ID、范围变更历史 |
| 专业分析观察及专业未知 | REA原生结果或对应工具原始结果 | 原ID、所属bundle/结果文件、摘要、确切选择范围 |
| 只有项目知道的缺口 | 项目任务，如缺用户材料或产品决定 | 问题、影响的需求、解决依据 |
| 实现/比较/构建/安装的结果 | 实际生产它的工具或受控执行器 | 结果引用、身份、范围、环境/依赖、限制 |
| 下一步和交付状态 | 对上述当前事实的投影＋宿主语义审查 | 哪条要求已有依据，哪条缺什么，何处需要人 |

原生未知项不再复制后在本地单独标resolved：引用其原ID，状态来自原生历史；项目特有未知另记。
原生bundle与项目要求是不同职责的持久材料，不把保留两者本身误认为重复账本。

用户可见状态至少分开：已观察、已实现、已验证、交付物已核对、仍缺资料。
不把它们压成一个含义过宽的“完成”；明确区分阶段成果与完整目标交付。
任务原话映射仍由宿主审查，不声称工具能自动理解全部语义或发现一切遗漏。

## 4. 核心改动：统一接入验证结果，而不是统一强制一种比较器

### 4.1 按问题选验证来源

| 问题 | 默认使用 | 自有层责任 |
|---|---|---|
| REA支持的行为/结构复刻主张 | 原生比较及适用的verify_reconstruction | 保存原始结果和主张范围，检查其当前适用性 |
| REA支持的覆盖/实现归属/义务 | 原生coverage/obligation工具 | 按真实任务需要调用，映射到用户需求，不再重做同一判据 |
| 网页操作、HTTP/WebSocket或异步观察 | 原生浏览器场景/比较 | 保存缺失、截断与观察窗口，不用截图替代业务 |
| 页面外观 | 像素/布局辅助检查 | 固定对应场景和宽度，保留截图、容差、动态区域与未覆盖项 |
| native Windows有限命令/输入/文件状态 | 当前自有有界比较器 | 保留自有身份及限制，不声称PTY、全GUI或完整网络覆盖 |
| APK设备、桌面GUI、安装升级、项目专用测试 | 对应实际工具或受控验证脚本 | 身份/范围绑定后接入；候选单测只证明候选符合声明规格，不证明原版等价 |

### 4.2 结果引用与检查

各适配器从真实结果读取：生产者、操作、文件/原ID、内容摘要、需求/场景、参照/候选身份、输入/环境绑定、观察维度、状态与限制。
这是内部结果索引，不再让智能体为每项结果手填一套复杂对象；能从工具回执取到的字段由适配器取。

- 不是增加一个可手填pass的record操作；只接受受控执行产生或可验证导入的受支持结果。
- 每种适配器验证对应schema、来源链及身份，不是“JSON里写pass就接受”。
- 缺失/截断/不兼容/失效只影响相应需求和观察维度；不能将弱证据升级为更强结论。
- 文件摘要一致只证明内容未变，不自动证明来源真实、语义充分或服务端状态未变。
- 原生验证结果保留原始含义；自有回执始终标owned，不包装成官方Evidence/proof。
- 只使用实际公开工具合同。当前没有公开的verify_reconstruction_obligations工具合同，不能猜同名接口或依赖私有内部函数作为产品入口。
- 如果某类结果不能满足REA正式接纳条件，就保留为自有验证；不伪造原生记录来追求“统一”。

### 4.3 交付门

只对用户要交付的范围检查：需求覆盖、所需参照依据、当前实现/包身份、适合该行为的验证、相关关键未知、实际交付文件。
静态依据、单元测试、原版对照、设备实测、干净安装分别表达，不能互相冒充。
有未知可交阶段成果，但剩余目标必须继续列出，不能把阶段成果写成完整目标已完成。
旧版本的本地通过不会自动升级为原生通过；来源链不足时按需重验，不要求无差别重跑所有历史任务。

## 5. 默认工作方式与减负

### 普通开发

宿主直接开发和测试，不建逆向case、不运行REA诊断；必要时使用共享磁盘管理。
已有宿主任务表能可靠保存需求时不另建平行待办；复杂逆向/复刻才建立薄项目视图。

### 简单分析

只记录回答问题所需的原始观察、结论、未知和报告。没有候选就不造实现、比较或包验收手续。

### 长任务/复刻

1. 保存原话，列出可观察行为和当前缺口；技术判断由智能体负责。
2. 当前问题需要时读取Reverse方法，直接使用合适的REA/宿主工具。
3. 按一个有价值的行为批次实现；读取实际差异后修正，必要时回调查。
4. 操作结果自动进入索引；在有意义的边界刷新要求/证据/验证和空间状态。
5. 交付时回看完整原话与补充，对实际候选和未完成项分别说明。

闭环仍在当前宿主内：工具结束产生可消费的差异和受影响需求，不新增后台AI。
宿主支持稳定工具结果钩子时可接；不支持时用短入口刷新和批次检查点，不宣称已自动截获全部原生命令。
默认不要求每条工具调用额外填写work item；重型/有副作用操作仍保留必要目标、资源与清理边界。
不要求每次编辑截图、重分析原版、干净重打包或再生成一份同义报告。

活动指令收敛为一份短工作合同和各类操作参考；用户指南/安装指南与专业方法分开。
初始自有公共指令暂定不超过6KiB UTF-8（不含按需官方schema/领域资料），这是减负目标，不是模型效果证明。
复杂领域材料在出现相关问题时再读；保留专业知识与来源，不为达到字节目标删除技术细节。

S2/S3只改实际需要的部分；存储、安装、租约已经可用的模块不为架构整齐重写。

## 7. 什么才算精简成功

### 7.1 工程门：可在无额外模型的独立材料上验证

- 当前9项修复反例继续通过；新增原生/自有两类结果真实接入。
- 同一主张错候选、原版替代、缺文件、截断、旧证据、错误适配器均不能产生合格交付。
- API/网络、界面、设备、构建和安装不会因“只能用进程/像素比较”被迫伪造检查。
- 白话原话、补充、剩余项在中断和搬家后保留；缺一个依赖不阻断无关功能。
- 单一MCP及官方工具合同保留；缺可选provider只影响相关工作。
- 写入/取消/回退失败保留真实结果；分级空间实际回收，保护材料摘要不变。
- 记录初始指令字节、实际结果回传体积、人工补写的记账次数、重复运行、耗时与磁盘峰值。

### 7.2 产品收益门：不能用工程测试替代

先比较“当前9项修复后的完整聚合”和“精简候选”，工具/模型/版本、初始材料、预算、权限与运行环境保持相同。
首轮用小型网页交互、Windows多文件状态程序、一次补充要求＋中断恢复等代表任务；设备/混合APK必须另有真实设备证据才能宣称覆盖。
保留未提前告知的验收输入与故意错误候选；不拿开发时已经训练过的同一示例当决定性结论。
模型试用应使用相互隔离的会话，避免后一条件继承前一条件的解题答案；不让同一测试作者的自述成为唯一验收。

若要进一步归因，再引入“同模型＋同工具＋REA简洁指导”的参照组；不要一开始铺设大型实验平台。
计量的是每个任务的真实完成质量/成本，不只比较一次调用的速度。
少量试用仅说明可行性；稳定效率优势需要重复和不同材料支持。

保留精简候选的最低判断：

1. 不新增严重误报完成、错交付或数据损失；必要隐藏场景通过，范围不缩水。
2. 相同质量下，入口负担/重复记账/重复验证有实际下降；耗时成本没有无法解释的持续恶化。
3. 真实收益不足的模块退出默认流程，不为证明聚合有用而降低验收要求或强留组件。

本方案审批只决定是否工程实施，不自动授权额外付费模型调用或第二模型循环。
模型收益实验的预算和宿主执行方式需在执行前明确；未执行就保留“效果未建立”，不能把工程完成包装成整体更强。

## 8. 兼容、回退和部署

- 先保留现有五个增强入口名称及CLI兼容；不引入第二个MCP登记。
- 旧case的原路径/摘要/原生ID保持；转换先输出到新副本，并保存转换记录。
- 当前9项修复基线、原始材料、用户配置、旧交付物均是保护对象，不列入“精简垃圾”。
- 先在独立临时home和成果项目验证，不运行历史安装器，不恢复旧真实目标。
- 改动当前editable checkout会影响新启动连接，旧连接会要求重连；不能把“不运行安装器”说成运行源码完全没变。
- 工程通过后仍需新源码绑定资格、公共安装/回退检查和支持环境验证，才能申请切换自有用户入口。
- 方案批准不等于授权提交、推送或切换部署；这些动作按用户后续明确要求执行。
- 功能/成本退化时退回S0实际修复基线和旧入口，保留新证据；不删除其他项目、历史未知材料或凭据。
