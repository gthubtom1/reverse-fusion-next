# 新聚合的作用、缺口与本轮修复

2026-11-17。依据换肤软件对话和现存工程，审阅点为case revision 351。完整目标软件不因本轮修复而自动验收；本轮未改动该工程或向其对话发送指令。

## 明确结论

现有工具层有实际作用，长任务组织层存在实质缺口。问题同时涉及宿主策略、聚合接口与验证机制，不能简化为“只是模型思路错了”。官方工具接通和返回成功，也不足以认定工具选择、调用频率和结论使用正确。

未做同模型、同工具、同目标、同预算的模型A/B，因而没有“聚合必然更强/更快”或“模型本身变笨”的实证结论。规则负担、冗长状态、过粗依赖和重复检查可能降低任务表现；本案例有这些具体开销迹象。聚合的价值应由更少遗漏、可靠恢复、可复用验证和正确交付来证明，不是由组件数量证明。

## 实际用了什么

| 层 | 实际使用 | 判断 |
|---|---|---|
| Reverse Skills | 领域路由、JS/桌面分析、复刻和先例资料已读取 | 方法入口生效；读过不等于所有方法均恰当应用 |
| 官方 REA | 识别、Ghidra选定函数反编译、Frida、证据导入导出等有成功记录，部分操作真实超时/不可用 | 工具有用；使用效率与每条结论仍需核对 |
| 本仓库增强层 | case、功能/未知、CLI/MCP、有限比较均使用；后半程多数外部报告仅作附件 | 使用不完整，运行控制未覆盖全部执行流 |
| Craft | 原版运行时没有运行；新版采用自主实现的比较/修正机制 | 本次不能归为Craft运行时故障；适配机制由本项目负责 |
| 宿主模型 | 实际推理、选方法、写代码、构建和调用工具 | 工具并非替代模型；优先级和结论错误也在此层发生 |

## 本案例的主要根因

1. 前端提取充分，部分后端仍无完整行为依据，“已全部分析透彻”的前提不成立。
2. 功能组过粗，未知项阻断整组，系统推荐与组内实际开发脱节。
3. 外部验证未持续接入声明检查；报告增加而统一完成状态没有同步推进。
4. 可变构建报告被多条历史证据引用，产生失效；需求补充又未全部持久登记。
5. 小改动频繁触发干净整包构建与相同验证；环境命令错误重复发生。
6. 部分验证对象错误：安装启动作者原版不证明候选自身升级；截图相似不证明后端和交互等价。

这是“有工具、有代码、有检查，但没有稳定减少关键产品差距”的组合问题。无壳降低分析门槛，不消除外部服务、状态与进程联动；这些剩余工作也不能为低效重复开脱。

## 2.2.0 的通用修复

- 观察默认冻结为内容摘要副本；活规格/源码依赖显式live，保留旧case原语义，不洗白历史证据。
- 状态省去重复历史输入快照，报告失效证据、缺检查、过粗功能、共享可变文件和长期未回比较的提示。
- 耗时脚本可选用既有record工具的execute操作：真实运行、记录输入/运行器/环境、日志、耗时、产物和取消清理。宿主工具仍可直达。
- 只有明确可复用的verify/package操作且声明输入/产物未变才复用；重复同输入失败需新信息，三次相同执行后回调查。执行成功不写验收pass。
- 声明候选/原版产品身份后，交付要求当前候选文件，识别把原版复制成候选；真实更新后的启动和行为仍需实际比较。
- 合同明确按变化选择验证，后端优先局部接口回放，UI查受影响交互及完整滚动，阶段集成或包变化才整包；没有组件打卡或固定截图循环。

同一现存case的只读输出比较：旧状态JSON 77,422字节，新状态19,718字节，减少约74.5%。这只是上下文输出体积，不是模型准确率、token费用或任务速度基准。一次本机取样新诊断计算还增加了约0.1秒，不能拿字节减少冒称所有性能提升。

## 面向不同目标的检查范围

| 类型 | 特有问题 | 共用处理机制 |
|---|---|---|
| 桌面/原生 | 多进程、多窗口、外部工具、DPI、安装升级 | 固定目标身份，记录运行环境，行为和视觉分开，阶段包验收 |
| APK | 设备/API/ABI、权限、原生库、资源和生命周期 | 工具按需路由；设备是依赖，独立功能继续，真实设备结果单列 |
| 网页 | 账号、网络、异步、存储、滚动、响应式 | 固定可观察状态/输入，比较交互与持久状态，不以首页截图关目标 |
| 混淆/壳 | 静态视图不足、运行时层变化 | 记录具体未知，选择能回答它的方法，新增证据后更新同case |
| 服务/协议 | 服务端逻辑缺失、时序、版本和外部状态 | 区分观察、推断和设计，保留缺依赖范围；候选测试不代替参照 |
| 任意长任务 | 补充遗漏、恢复漂移、反复重试、验收对象偏移 | 完整目标/功能/依据/差异同记录、不可变观察、成本和重试诊断、候选身份 |

这张表是检查维度，不是预设每个目标走同样路线。零基础用户不负责选工具和补专业提示词。

## 对裸AI加工具的判断

能力足够的宿主加相同工具与简洁提示，完全可以完成很多分析和复刻任务；增强层不是赋予模型智力的必要条件。它应降低长任务遗漏和重复。若规则消耗高于收益，精简规则、保留工具和宿主判断是正确方向。

公平评估应把同一模型、工具、初始材料和预算固定，分别使用精简提示和聚合；从未参与开发的输入/场景评估真实行为、需求遗漏、错误宣称、重复操作、时间及成本。不能比较不同模型/工具后把差异归给聚合，也不能用工程回归代替模型A/B。

未来任意目标的问题不能靠一次枚举证明穷尽。本轮可完成的是已发现根因的通用修复、失败反例和准确边界；后续新能力依靠可扩展工具/方法和受影响检查验证，不给每个软件堆固定补丁。
