# 业务代码审查与原程序修正

## 输入

收集用户原话、原程序及修订、触发问题的业务输入、状态起点、预期结果及持久化约定。确认交付口径是审查报告、修改现有程序或按规格实现。固定原程序与样本摘要，试验使用独立业务数据副本。

## 判读

1. 写清业务不变量，沿输入解析、校验、状态变化、持久化和错误出口逐步追踪。把现象绑定到程序中的文件、函数和分支。若多份报告指向同一修正点，则归并根因，同时保留不同入口和触发条件。
2. 用可重放的最小业务输入观察原版行为，保留退出码、输出、前后状态及写入文件。优先覆盖金额、数量、重复操作、边界值和失败路径，按题面区分应接受、应拒绝及不应改动的状态。
3. 用户要求修复时，保持业务接口和已约定的错误顺序。整单提交场景可先在临时状态累计检查，整单有效后一次提交。处理重复条目的累计用量，保留前一单已提交的变化。结果中列出原版问题、修正位置和已覆盖范围。

## 核对

同一反例从干净状态分别运行原版和修复版，验证原版确有失败、修复达到预期。补成功用例、边界及失败后的下一笔操作，回读真实数据状态。若业务约定涉及并发或断电恢复，按实际事务及持久化机制独立检验。

## 反例

一单先借 3 本现货，后一条因缺货整单拒绝。只断言报错文本会漏掉前一条已扣库存。另一用例在同一单两次借同一本书，各行单看都有货，合计超库存时整单应拒绝且库存原样保留。
